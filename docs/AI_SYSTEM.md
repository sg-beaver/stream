## 1. 개인정보 비식별화 (`scheduler/deidentify.py`)

### 문제

Gemini는 외부 서비스입니다. 네 경로 모두 프롬프트에 **학번·이름을 원문 그대로**
넣고 있었고, 특이사항·대타 사유는 학생이 자유 서술한 문장이라 연락처·이메일까지
섞여 나갔습니다. 실데이터로 운영하면 개인정보를 제3자에게 넘기는 일이 됩니다 (#200).

### 설계

```
컨텍스트 조립 (DB에서 배정·정책·자연어 규칙)
   ↓
mask()   학번·이름 → S01, S02 …   연락처·이메일·주민번호 → 삭제
   ↓
Gemini
   ↓
restore()  별칭 → 실제 표기 (+ 조사 교정)
   ↓
화면 / DB
```

**해시가 아니라 요청 단위 매핑**입니다. 되돌려야 하기 때문입니다. 매핑은 메모리에만
있고 요청이 끝나면 사라지므로, 프롬프트와 LLM 제공자 로그에 남는 것은 별칭뿐이고
그 별칭이 누구인지는 이 프로세스 밖에서 알 수 없습니다.

**프롬프트를 조립한 다음 통째로** 마스킹합니다. 섹션마다 치환하면 새 섹션이 늘 때
빠뜨립니다 — 실제로 그런 자리가 생겼습니다 (아래 '하네스 정합').

| 다루는 방식 | 대상 | 이유 |
|---|---|---|
| 별칭으로 치환 (되돌림) | 학번, 이름(2자 이상) | 판단에 필요하고 화면에 돌려줘야 한다 |
| 삭제 (되돌리지 않음) | 전화번호, 이메일, 주민번호 | 판단에 쓸 일이 없다. DB에 목록이 없어 패턴으로만 잡는다 |
| 애초에 넣지 않음 | 학과, 재원 구분, 생년월일, 국적, 지도교수 | 프롬프트 조립 함수 어디에서도 읽지 않는다 |

복원 형태는 자리마다 다릅니다 — `id`(구조화 필드 `target_id`처럼 값이 곧 키인 자리)
· `name`(챗봇 응답, 담당자는 이름으로 읽는다) · `name_id`(`이름(학번)`, 검토 의견처럼
대상을 확정해야 하는 자리).

### 설계에서 어려웠던 세 가지

**① 한글 조사가 어긋납니다.** 조사는 모델이 **별칭을 읽은 발음**에 맞춰 고릅니다.
`S02`는 "에스공이"로 끝나 받침이 없어 `S02는`이, `S03`은 "삼"으로 끝나 받침이 있어
`S03이랑`이 나옵니다. 이름을 도로 넣으면 그 이름의 받침과 어긋납니다 —
`조수현는`, `김찬우이랑`.

이름 뒤에 "학생"을 붙여 받침을 고정하는 안은 별칭 끝자리가 2·4·5·9(이·사·오·구)일 때
받침 없는 조사가 나와 절반만 고쳐집니다. 그래서 **복원한 이름의 받침을 보고 조사를
다시 고릅니다** — `(으로/로)·(이랑/랑)·(은/는)·(이/가)·(을/를)·(과/와)` 6쌍, `으로/로`만
ㄹ 받침 예외. 조사 뒤에 한글이 이어지면(`S03이라고`의 `이라`) 낱말의 일부라 손대지
않습니다. 학번으로 복원하는 자리는 발음을 알 수 없어 그대로 둡니다.

> 이건 실제 모델 출력을 관측하고 고친 게 아니라 **별칭 형식에서 추론한 위험**을 미리
> 막은 것입니다. LOG.md 2026-08-30 항목에 그렇게 적혀 있습니다.

**② 같은 학생이 두 번 접힙니다.** `20261004 박서연`·`박서연(20261004)`처럼 학번과
이름을 나란히 적은 표기는 둘 다 같은 별칭이 되어 `S04 S04`로 겹칩니다. 마스킹 뒤 한
번 접습니다 — 다만 **줄바꿈은 접지 않습니다.** 배정 결과처럼 같은 학생이 줄마다
반복되는 목록을 한 줄로 합치면 근무 건수가 사라집니다.

**③ 배정된 학생만으로는 부족합니다.** `build_for_department`는 판단 대상이 아니어도
**부서 소속 학생 전원**을 매핑에 넣습니다. 배정된 학생만 넣으면 특이사항·부서 규칙
원문에 등장하는 다른 학생 이름이 치환되지 않고 나갑니다.

### 실측 (LOG.md 2026-08-30, #200)

프롬프트에 남은 식별자 수를 직접 셌습니다. 학생 5명·부서 규칙 2줄(한 줄은 학생 이름
직접 지목)·특이사항 2건(연락처·이메일 포함)·배정 3건으로, `review_batch` 1회와
`chat.run_turn` 1턴에서 학번 5개·이름 5개·전화번호·이메일 **총 12개 문자열의 출현
횟수**를 셈. LLM 호출은 mock이라 모델 품질은 이 측정에 포함되지 않습니다.

| | `LLM_DEIDENTIFY=0` | `LLM_DEIDENTIFY=1` (기본) |
|---|---|---|
| review 프롬프트 | 식별자 **23건** / 1,799자 | 식별자 **0건** / 1,695자 |
| chat 1턴 전송 | 식별자 **30건** / 1,927자 | 식별자 **0건** / 1,835자 |

특이사항 문장("같은 시간은 피하고 싶어요")과 부서 규칙 문구는 그대로 남아 **판단
근거는 줄지 않았습니다.**

**검출력 A/B** (`gemini-3.7-flash`, 26케이스 × 2라운드 × 2조건 = 104회):
실명 프롬프트 **52/52 (100%)**, 별칭 프롬프트 **51/52 (98%)**, 양쪽 호출 실패 0건.

갈린 1건(`closing-gap`)은 비식별화 탓이 아니라 흔들리는 케이스입니다 — 그 케이스만
조건당 6회씩 다시 재니 **실명 5/6, 별칭 6/6으로 뒤집혔습니다**(두 실행 합산 7/8 대
7/8로 동일). 기대 키워드가 `'21:00'`·`'마감'`이라 학번·이름 치환이 닿는 축이
아닙니다. **26케이스 범위에서 별칭 치환으로 검출력이 떨어진 증거는 없습니다.**

**부수 효과 — 더 싸고 빨라졌습니다.** 별칭이 "학번 + 이름"보다 짧아 호출당 토큰
**4,813 → 4,653 (-3.3%)**, 평균 응답 **5.0초 → 4.5초**(최대 11.3초 → 9.4초).

**하네스 정합** — `eval_review.py`가 `review_batch`를 건너뛰고 `_build_prompt`를 직접
불러 **마스킹을 우회하고 있었습니다.** 그대로 두면 서비스는 별칭 프롬프트를, 하네스는
실명 프롬프트를 재게 됩니다. `run_case`에 프로덕션과 같은 자리(마스킹 → 호출 → 복원)를
넣어 맞췄습니다. 확인: `tenure-relative-comparison` 케이스 프롬프트 1,097자에 남은
식별자 0건, 별칭 `S01`·`S02`, 응답은 `오규원(20211357)`로 복원.

**단위 테스트** — `tests/scheduler/test_deidentify.py`:


## 2. LLM 없는 결정적 검증 (`scheduler/verify.py`)

### 문제

AI 검토(`review.py`)는 **draft 배치의 자연어 운영 규칙**만 봅니다. 확정된 배치가
SCHEDULER_SPEC 3장의 Hard Constraint를 실제로 지키는지 확인할 경로가 없어, 솔버를
거치지 않고 손으로 넣은 배치가 `confirmed`로 남아도 어디서도 걸리지 않았습니다 —
실제로 시드 데모 배치가 그 상태였습니다.

### 설계

`verify_batch(db, batch_id)`는 **솔버와 같은 정책·캘린더·가용시간 로더**를 태워 배치를
다시 채점합니다. 추가 경로가 자기만의 기준을 두면 "추가는 되는데 검증기는 위반이라는"
상태가 생기기 때문입니다.

**여기서 나온 위반은 "AI가 그렇게 볼 수도 있다"가 아니라 실제로 규정을 어긴
배정입니다.** LLM이 개입하지 않으므로 같은 입력에 항상 같은 답이 나옵니다.

`status`와 무관하게 동작합니다 — draft·confirmed·manual 어느 쪽이든 "이 배정이 규정을
지키는가"는 같은 질문입니다.

| 채점하는 것 | 규칙 |
|---|---|
| 개관 시간 밖 배정 | `HC-OPEN` |
| 제출한 가능 시간 밖 배정 | `HC-CLASS-1` |
| 근로 활동 기간 밖 배정 | `HC-CLASS-6` |
| 시간대별 최소·최대 인원 | `HC-STAFF-1` / `HC-STAFF-2` |
| 주간 상한 (교비/국가) | `HC-TIME-1` / `HC-TIME-2` |
| 국가근로 월 상한 | `HC-TIME-3` |
| 부서 교비 2주 총합 상한 | `HC-TIME-4` |
| 솔버 산출물이 아닌 배치 | `PROVENANCE` (warning) |

**의도적으로 채점하지 않는 것 둘**이 있고, 둘 다 이유가 있습니다.

- `HC-BLOCK-1`(블록 all-or-none) — 확정 근무표를 운영 중에 고치는 일(부분 대타 승인)은
  블록을 쪼개는 **허용된 운영 예외**입니다 (SPEC 3.5, #123). 생성 시점 제약을 확정본에
  들이대면 정상 대타가 전부 위반으로 잡힙니다.
- `HC-CLASS-2`(수업 시간 겹침) — DB에 학생 수업 시간 소스가 없어 "가용 시간에 없으면
  수업 중"으로 간접 처리합니다 (SPEC 2.1). `HC-CLASS-1` 검사가 이를 함께 덮습니다.

`PROVENANCE`가 warning인 것과 마찬가지로, **`ok` 판정은 critical만 봅니다.** 최소 인원
미달(warning)은 해가 없다는 뜻이 아니라 담당자 판단 몫이라 통과를 막지 않습니다.
응답에는 `coverage`(개관 슬롯 대비 최소 인원을 채운 비율)도 함께 담아, "규정을
지켰는가"와 "꽉 찼는가"를 나눠 볼 수 있게 했습니다.

### 어디에 연결돼 있는가

| 소비처 | 쓰임 |
|---|---|
| `GET /api/schedule/verify` | 담당자가 배치 하나를 직접 채점 |
| 챗봇 읽기 툴 `verify_schedule` | "규정 지키나" 질문에 짐작하지 않고 채점해서 답한다 |
| 챗봇 쓰기 툴 (자동) | 편집 **전후 위반 차집합**을 결과에 얹는다 |

세 번째가 핵심입니다. **모델이 검증을 부를지에 기대지 않습니다** — 편집이 새로 만든
critical 위반을 항상 결과에 붙입니다. warning(인원 부족)은 제외합니다: 근무를 옮기면
거의 항상 자리가 바뀌어 매 편집마다 딸려 오고, 그러면 진짜 위반이 묻힙니다.

이 연결이 [ARCHITECTURE.md](ARCHITECTURE.md)의 공용 검증 모듈이 덮지 못하는 제약
(`HC-CLASS-1`·`HC-CLASS-6`·`HC-STAFF`·`HC-TIME-3/4`)을 메웁니다.

### 실측 (LOG.md 2026-08-30, #195)

시드 DB의 실제 draft 배치(부서 2, 2026-08-31\~09-13, **55행**)로 비용을 쟀습니다.

```
verify_batch  0.023 ~ 0.037s   (3회 측정)
```

편집마다 전·후 두 번 돌려도 부담이 없는 값입니다. 같은 편집이 그 뒤로

```json
new_violations: [{ "rule": "HC-CLASS-1",
                   "student": "조수현(20223333)",
                   "when": "2026-09-07 20:00-22:00" }]
```

을 함께 돌려주고, 실제 Gemini가 그것을 답변으로 옮겼습니다 — *"다만 이번 변경으로
규정 위반이 새로 발생했습니다. … 이대로 유지하시겠습니까, 아니면 되돌리거나 다른
시간대를 찾아볼까요?"*

**단위 테스트** — `tests/scheduler/test_verify_batch.py`:

## 3. AI 품질 평가 하네스 3종 (`scripts/eval_*.py`)

### 왜 필요한가

프롬프트를 고쳤을 때 좋아졌는지 나빠졌는지는 **재지 않으면 알 수 없습니다.** LLM
출력은 비결정적이라 한 번 돌려 본 인상으로는 판단이 서지 않습니다. 세 하네스는 모두
**케이스를 코드가 아니라 JSON으로 관리**해(케이스 추가에 코드 변경이 필요 없게) 같은
조건으로 전후를 비교할 수 있게 합니다.

| 하네스 | 대상 | 케이스 | 격리 |
|---|---|---|---|
| `scripts/eval_review.py` | AI 검토 (`review.py`) | 26 (`eval_review_cases.json`) | DB 없이 가짜 객체로 프롬프트 조립 |
| `scripts/eval_chat.py` | 시간표 챗봇 (`chat.py`) | 21 (`eval_chat_cases.json`), 3층 | **케이스마다 in-memory sqlite 새로 생성** |
| `scripts/eval_substitute_check.py` | 대타 적합성 검사 | 2 (`ok` · `clarify`) | DB 없이 가짜 객체 |

전부 CI 밖 수동 실행입니다(실제 모델 호출·비용). 결과 JSON은
`backend/output/eval_*.json`에 남기고 gitignore 대상입니다.

**챗봇만 DB를 새로 만드는 이유**는 챗봇에 쓰기 툴이 있기 때문입니다. 개발 DB를 그대로
쓰면 계측이 실제 draft를 바꿉니다.

**세 하네스 모두 비식별화를 프로덕션과 같은 자리에서 지납니다** — 마스킹 → 호출 → 복원.
`eval_chat.py`는 `run_turn`을 그대로 불러 자동으로, 나머지 둘은 `run_case`가 그 순서를
직접 밟습니다(검토 2026-08-30, 대타 검사 2026-09-01). 이 자리를 빠뜨리면 서비스는 별칭
프롬프트를, 하네스는 실명 프롬프트를 재게 되어 **여기서 잰 검출력이 실제 검출력이
아니게 됩니다.**

### 재는 축

검토·대타 검사는 **검출력**이 축입니다 — 위반 케이스에서 잡아내는가, 위반이 없는데
critical을 내는가(오탐), 되묻지 말아야 할 때 되묻는가.

챗봇은 draft를 **직접 고치므로** 틀렸을 때의 비용이 달라 축이 더 많습니다.

- 툴 선택 정확도 — 물어본 것에 맞는 툴을 부르는가
- `find_schedules` 선행률 — `schedule_id`를 추측하지 않고 조회하는가
- 요청하지 않은 수정 비율 — 질문했는데 근무표를 고치는가
- hard 제약을 깨는 편집 비율 — 결과에 `new_violations`가 붙는가
- **확인 전 단정** — 조회하지 않은 것을 사실처럼 말하는가
- 예산 소진률 · 턴당 툴 호출 수 · 응답 시간 · 토큰

`forbid_text_any`(답변에 있으면 실패) 축은 나중에 추가됐습니다. 있어야 할 말을 재는
`expect_text_any`로는 **"확인하지 않은 것을 단정하는" 실패를 잡을 수 없기** 때문입니다.
문구는 좁게 잡습니다 — `"동일합니다"`처럼 넓히면 "요일 표는 동일합니다, 다만 폐관일이…"
라는 **옳은** 답까지 실패로 셉니다.

### 하네스가 스스로를 틀리게 만든 사례

계측기를 믿기 전에 계측기를 의심해야 한다는 것을 두 번 배웠습니다.

- **거짓 통과** — `overstaffing-edit-is-reported`가 통과했는데 실제로는 위반이 생기지
  않았습니다. 기본 정책의 `max_per_slot`이 2라 두 명을 같은 칸에 넣어도 위반이
  아니었고, 모델은 "규정 위반은 **없습니다**"라고 답했는데 기대 키워드 `"위반"`이 그
  **부정문에 매칭**됐습니다. `max_per_slot=1` 시나리오를 만들고 판정을 구조적 축
  (`expect_new_violations`)으로 바꿔 고쳤습니다.
- **마스킹 우회** — 1절의 '하네스 정합'. 하네스가 프로덕션과 다른 경로를 타고
  있었습니다. `eval_review.py`(2026-08-30)와 `eval_substitute_check.py`(2026-09-01)
  **두 곳에서 같은 모양으로** 나왔습니다.

### 실측

**AI 검토** (LOG.md 2026-08-30 최신 라운드, `eval_review.py`, `gemini-3.7-flash`,
현재 케이스 세트 26개 × 2라운드)

```
52/52 (100%), 호출 실패 0건
평균 응답 5.3s / 최대 10.1s
호출당 4,822 토큰 (프롬프트 18줄 추가로 4,402 → 4,822, 약 +9.5%)
```

바로 앞 라운드는 같은 26케이스에서 **49/52 (94%)** 였고, 실패 2건(`rule-conflict`·
`note-ambiguous-clarify`)을 프롬프트 세 곳 수정으로 각각 5/5로 올린 결과가 위
수치입니다. 두 케이스는 비결정적이라 **5회씩 따로** 쟀습니다 — `rule-conflict`는
2회 표본에서 "결정적 실패"로 보였지만 5회로 재니 3/5(60%)로 흔들리는 쪽이
실상이었습니다.

**모델 세대 비교** (당시 18케이스·같은 프롬프트, 변경점은 모델명뿐, 모델당 2라운드)

| | gemini-3.5-flash | gemini-3.7-flash |
|---|---|---|
| 검출률(2라운드 합계) | 35/36 | **36/36** |
| 평균 응답시간 | 5.3s | **4.1s (-23%)** |
| 호출당 토큰 | 4,567 | **4,124 (-10%)** |

이 측정을 근거로 `review.py`·`chat.py`의 기본 모델을 3.7-flash로 올렸습니다. provider는
REQ-SCHED-016대로 Gemini 고정이고 **세대만** 올린 것입니다.

**챗봇** (LOG.md 2026-08-31, `eval_chat.py --repeat 3`, `gemini-3.7-flash`, 실제 Gemini
호출, 2회 실행, 21케이스)

```
63/63 (100%) — basic 18/18, edit 21/21, guard 24/24, 호출 실패 0건
턴당 툴 2.22회 / 2.21회,  쓰기 25건 / 24건
예산 소진 0턴 · 부분 실패 0턴 (두 실행 모두)
턴 소요 평균 8.7초 (최대 22.6초), 턴당 토큰 평균 15,606
```

통과 여부는 두 실행이 같고 축 수치만 1씩 흔들립니다 — **`temperature=0`이어도 툴 호출
수는 완전히 결정적이지 않습니다.** "제약 위반을 만든 쓰기 6건"은 전부 그걸 의도한
케이스(`expect_new_violations: true`)에서 나온 것입니다.

**대타 적합성 검사** (LOG.md 2026-09-01, `eval_substitute_check.py`, `gemini-3.7-flash`,
케이스 2개, 3라운드 연속, **비식별화 적용 후**)

```
3라운드 모두 2/2 (ok · clarify), 호출 실패 0건
wall-clock 17.3s / 14.9s (2·3라운드, 모듈 임포트 1.00s 포함)
프롬프트 551자 (ok) · 554자 (clarify), 남은 식별자 0건, 별칭 S01·S02
```

같은 조건의 마스킹 우회 시절 라운드는 35.0s / 21.1s였습니다. **이 차이를 수정의 효과로
읽으면 안 됩니다** — 같은 실행 안에서도 1라운드가 62.8초로 4배 넘게 튀고, 마스킹으로
줄어든 프롬프트는 14자입니다. 케이스 2개·라운드 3회 표본에서 이 폭은 라운드 간 편차와
구분되지 않습니다. 이 수정으로 확실해진 것은 속도가 아니라 **재는 프롬프트가 서비스가
보내는 프롬프트와 같아졌다**는 것 하나입니다.

`clarify` 케이스의 실제 출력 — 근속 정보가 없는 후보에 대해 단정하지 않고 되물었습니다.

```json
{ "overall_verdict": "판단불가",
  "clarification_requests": [{
      "target_type": "student", "target_id": "20222222",
      "field_name": "tenure_start_date",
      "question": "학생 학생B(20222222)의 근속 시작일(tenure_start_date)은 언제인가요?",
      "reason": "부서 운영 규칙인 '금요일 마감 시간대(17시 이후)에는 경험자가 최소 1명
                 있어야 한다' 충족 여부를 확인하기 위해 학생의 근속 정보가 필요합니다." }] }
```

> 위 출력의 `target_id`가 실제 학번인 것은 **복원까지 마친 값**이기 때문입니다. 모델이
> 받은 프롬프트에는 `S01`·`S02`만 있고 8자리 학번·이름은 0건이며, 응답의 `S02`가
> `학생B(20222222)`로 되돌아온 것입니다 — 프로덕션(`substitute_check.py:182-191`)과 같은
> 순서입니다. 2026-09-01 이전 라운드는 이 네 단계를 하나도 타지 않아 **실명 프롬프트
> 기준**이었고, 그래서 검토·챗봇 수치와 나란히 둘 수 없었습니다. 지금 수치는 나란히 둘
> 수 있습니다.
>
> 마스킹 후에도 `clarify` 케이스는 그대로 `판단불가` + `tenure_start_date` 되묻기를
> 냅니다 — **별칭으로 바꿔도 검출력이 죽지 않는다**는 1절의 결론(51/52)과 같습니다.

### 알려진 한계 — 계측기 포화

**검토와 챗봇 모두 케이스를 전부 통과합니다.** 만점이라 다음 변경이 좋아졌는지
나빠졌는지 가릴 수 없습니다. 하네스 자신이 전 케이스 통과 시 **"계측기 포화" 경고를
출력**하도록 만들어 뒀는데, 검토에서 세 번, 챗봇에서도 반복해서 그 경고가 떴습니다
(#195).

**점수가 낮은 게 아니라 만점이라 못 쓰는 계측기**라는 것이 그 측정들의 결론입니다.
케이스를 어렵게 늘리는 것이 다음 할 일이며 이슈 #195에 올라와 있습니다.

그 밖에:

- **"severity가 1단계"로 보였던 것은 계측기 탓이었습니다.** findings가 계속 전부
  critical로 나와 모델이 severity를 못 가른다고 적었는데, 그때 케이스 세트에
  **warning을 기대하는 케이스가 하나도 없었습니다.** 특이사항 케이스 3개를 넣자
  findings 39건 중 **warning 4건**이 나왔고 `note-soft-violation`이 2/2로 통과했습니다.
  계측기의 결론을 계측기의 입력 범위와 함께 읽어야 한다는 사례입니다.
- **하네스가 프로덕션과 다른 경로를 재는 일은 두 번 있었고 둘 다 닫혔습니다.**
  `eval_review.py`가 2026-08-30, `eval_substitute_check.py`가 2026-09-01에 마스킹을
  우회하고 있었습니다. 대타 검사 쪽은 **한 번도 실행된 적이 없어(LOG·`output/` 어디에도 기록이
  없었습니다) 드러나지 않았습니다** — 돌려 보지 않은 계측기는 틀린 줄도 모릅니다. 이제
  셋 다 프로덕션 경로를 지나지만, 이 축은 하네스를 새로 만들 때마다 다시 확인해야
  합니다(자동으로 검사되지 않습니다).
- **provider 간 토큰 수치는 직접 비교할 수 없습니다.** Gemini의 `total_token_count`는
  사고(thinking) 토큰을 따로 포함해 입력+출력보다 크고, Claude는 구조화 출력이 없어
  JSON 스키마 전체를 매 호출 넘기는 하네스 구현상 오버헤드가 있습니다. 같은 provider의
  라운드 간 비교로만 씁니다.
