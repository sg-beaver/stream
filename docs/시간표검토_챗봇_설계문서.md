# 시간표 검토 챗봇 — 설계 문서

**작성일**: 2026-08-27
**개정일**: 2026-08-28 (v2 — 에이전트 전환·가중치 튜닝 반영, 섹션 0.1 참고)
**관련 배경**: 되묻기(clarification) 기능, 대타 승인 AI 적합성 검사(`ai-check`) 기능의 연장선. 근무표 검토를 여러 턴 대화형 챗봇으로 확장하는 기능.
**전제**: 되묻기 인프라(`clarification_requests`, `clarification_answer`), `review` 기능, `POST /api/schedule/manual`(직원 수동 배정 API, #77에서 겹침·주간 상한 검증 완비)이 모두 구현·머지 완료된 상태.

---

## 0. 배경 및 목표

기존 `review`는 1회성 배치 호출로 findings/clarification_requests를 반환하는 stateless 구조다. 직원이 특정 배정에 대해 자유롭게 캐묻고("이건 왜 이래?", "이 학생 빼고 다시 봐줄 수 있어?"), 대화 중 나온 변경 아이디어를 그대로 반영할 수 있는 대화형 인터페이스가 필요하다는 문제의식에서 출발한다.

**핵심 원칙**: 챗봇은 **draft(제안) 근무표만** 고친다. 확정(`confirm`)은 사람만 한다. "AI는 확정 권한이 없다"는 프로젝트 전체 원칙은 유지하되, 그 게이트를 턴마다가 아니라 확정 시점 한 곳에 둔다.

## 0.1 v2 개정 배경

v1은 AI가 변경을 "제안"만 하고 직원이 턴마다 승인 버튼을 눌러야 반영되는 구조였다. 두 가지 피드백에서 개정이 출발한다.

1. **가중치를 대화로 찾자.** 현재 soft constraint 가중치는 임의로 정한 값이고 실제 사용자의 체감과 다를 수 있다. 대화하면서 적절한 가중치를 좁혀 나가는 방식이 낫다.
2. **제안만 하는 건 번거롭다.** draft 시간표를 바꾸는 것이니 AI가 직접 반영하고, 결정(확정)만 사람이 하면 된다.

### 개정 착수 전 코드 조사 결과 (v1 섹션 8의 선행 조사)

조사 결과 v1 설계의 **핵심 전제 두 개가 실제 코드와 어긋난다**는 것이 확인됐다.

## 0.2 두 기능의 관계 — 순서를 강제한다

가중치 조정(전역 재배치)과 개별 편집(국소 수정)은 **서로 충돌한다.** 챗봇으로 손수 고쳐 놓은 배정이 있는 상태에서 가중치를 바꿔 재solve하면 그 수정이 전부 사라진다. 사용자는 같은 대화창 안에서 이 둘을 구분하지 못한다.

이번 단계에서는 **순서 강제**로 해결한다.

```text
① 가중치 대화 (전역 튜닝, 재solve)  →  ② 개별 편집 (국소 수정)  →  ③ 확정
```

- ② 이후 ①로 되돌아가는 요청이 오면 "수동 수정 N건이 사라집니다"를 경고하고 사용자 확인을 받는다.
- 수동 수정분을 hard constraint로 고정(pin)한 채 재solve하는 방식은 고정이 늘수록 `INFEASIBLE` 위험이 커지므로 이번 단계 스코프 밖으로 둔다(섹션 7).

## 2. 데이터 스키마

### `chat_session` (신설)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `session_id` | PK | |
| `department_id` | FK → `department` | 세션이 묶인 부서 (결정 9) |

`batch_id`를 nullable로 두고 기간 기준으로 draft를 다시 찾는 방식도 가능하나, 조회 편의를 위해 현재 배치를 캐시하고 재생성 시 갱신한다.

| 컬럼 | 타입 | 설명 |
|---|---|---|

## 3. API 스펙

### `POST /api/schedule/chat/sessions`
새 세션 생성. Body: `{ "department_id": int, "period_start": date, "period_end": date }`. 해당 기간의 draft 배치를 찾아 `batch_id`에 캐시한다. draft가 없으면 400.

### `GET /api/schedule/chat/sessions/{session_id}/messages`
대화 이력 전체 조회 (새로고침 후 복원용, 결정 3).

### `POST /api/schedule/chat/sessions/{session_id}/messages`
메시지 전송. Body: `{ "content": string }`. 최근 N턴(결정 10)을 컨텍스트로 포함해 Gemini 호출 → 분류 결과에 따라 분기한다.

**`edit` 응답 예시** — 변경이 이미 적용된 상태로 반환된다.
```json
{
  "message_id": 42,
  "role": "assistant",
  "content": "8/28 수요일 20211357 학생의 근무를 13:00-18:00로 옮겼습니다. 되돌리려면 알려주세요.",
  "response_type": "edit",
  "applied_change": {
    "op": "move",
    "schedule_id": 255,
    "start_time": "13:00:00",
    "end_time": "18:00:00"
  },
  "inverse_change": {
    "op": "move",
    "schedule_id": 255,
    "start_time": "09:00:00",
    "end_time": "14:00:00"
  },
  "edit_status": "applied"
}
```

검증(겹침·주간 상한) 실패 시에는 변경 없이 `edit_status: "failed"`와 함께 실패 사유를 그대로 담아 반환한다.

**`tune` 응답 예시** — 가중치를 조정하고 재solve한 결과.
```json
{
  "message_id": 43,
  "role": "assistant",
  "content": "식사 시간 확보를 더 중요하게 잡고 다시 짰습니다. 식사 누락 페널티가 60에서 20으로 줄고, 대신 선호 시간대 미충족이 12에서 21로 늘었습니다.",
  "response_type": "tune",
  "weight_change": { "category": "meal_missed", "direction": "up", "before": 1.0, "after": 1.5 },
  "penalty_diff": {
    "before": { "meal_missed": 60, "preferred_slot_miss": 12 },
    "after":  { "meal_missed": 20, "preferred_slot_miss": 21 }
  }
}
```

### `POST /api/schedule/chat/sessions/{session_id}/messages/{message_id}/revert`
`edit` 메시지 되돌리기. `inverse_change`를 적용하고 `edit_status = "reverted"`로 갱신한다.

- 이미 `reverted`/`failed`인 메시지: 409
- 되돌린 변경은 재적용 불가 — 사용자가 새 메시지로 다시 요청해야 한다 (결정 11)

### `POST /api/schedule/chat/sessions/{session_id}/weights/persist`
세션의 `session_weight_scales`를 부서 기본값(`department_policy.soft_weight_scales`)으로 저장한다 (결정 15). 기존 PATCH 경로(`routers/schedule.py:1093-1099`)를 재사용한다.

## 4. 프롬프트 설계

**신규 파일**: `chat_system_prompt.md` (review, substitute_check와 별도 — 기존 패턴대로 용도별 분리)

### 4.1 공통

포함할 요소:
- 이 세션이 다루는 기간의 현재 draft 근무표 상태, 부서 `custom_rules`, 현재 `penalty_breakdown`
- 최근 N턴의 대화 이력
- **분류 강제**: 사용자 발화를 `answer` / `edit` / `tune` 중 하나로 분류하고, `edit`이면 `op`·`schedule_id`·시각이 스키마에 맞게 나오도록 명시
- **원칙 문구**: "너는 제안(draft) 근무표만 고칠 수 있다. 확정은 사람만 한다. 네가 고친 내용은 되돌릴 수 있다."

### 4.2 가중치 조정 — LLM에 숫자를 맡기지 않는다 (결정 13)

"`meal_missed`를 20에서 30으로" 같은 숫자를 LLM이 직접 고르게 하면 근거 없이 요동친다. 파이프라인을 다음과 같이 고정한다.

```text
사용자 자연어 불만
  → LLM은 [카테고리 + 방향]만 분류 (예: meal_missed / up)
  → 시스템이 고정 스텝으로 배율 적용 (up = ×1.5, down = ×0.67)
  → 결정적 재solve (결정 14)
  → penalty_breakdown before/after를 사용자에게 제시
```

이렇게 하면 LLM 호출은 턴당 1회로 유지되고(섹션 6.1 쿼터 위험이 커지지 않음), 비용은 solver 쪽으로 옮겨간다.

**조정 대상 카테고리** (`config/departments/library_info_service.json`의 `soft_weights`):
`preferred_slot_miss`(3), `block_start`(4), `non_campus_day`(5), `fair_hours_shortfall`(6), `morning_days_excess`(10), `consecutive_morning_excess`(10), `avoid_range_slot`(12), `morning_after_close`(15), `meal_missed`(20), `exam_proximity`(25).

`understaffing`(1000)은 hard에 준하는 값이므로 **대화형 조정 대상에서 제외한다.**

### 4.3 결정적 재solve (결정 14)

사실 E에 따라, 가중치를 바꾸지 않아도 재생성만으로 시간표가 달라진다. 비교가 성립하려면 재solve를 결정적으로 만들어야 한다.

- `solver.parameters.random_seed` 고정
- `solver.parameters.num_search_workers = 1`
- 동일 `time_limit_seconds` 사용

**선행 작업**: 이 파라미터 설정은 `scheduler/engine/solver.py`에 현재 없다(사실 E). 챗봇 구현 착수 전에 먼저 넣고, 동일 입력 2회 실행이 동일 결과를 내는지 실측으로 확인해야 한다. 이 확인 없이 가중치 대화 기능을 만들면 노이즈에 반응하는 챗봇이 된다.

**부작용**: 단일 워커는 느리다. 프로덕션 규모에서 이미 30초 제한에 걸려 `FEASIBLE`로 끝나므로(사실 E), 대화 턴 안에서 동기로 돌리기에는 길다. 비동기 처리 또는 비교용 짧은 `time_limit` 사용을 함께 검토한다.

## 5. 적용·되돌리기 처리 로직

```python
def apply_edit(session, change, staff):
    """draft 배치의 근무 한 건을 고친다. manual 배치는 건드리지 않는다 (사실 A·B)."""
    row = get_draft_schedule(session.batch_id, change["schedule_id"])
    inverse = snapshot(row)                      # 변경 전 상태 — 되돌리기 근거

    _check_no_overlap(db, row.student_id, new_date, new_start, new_end)
    _check_weekly_hour_limits(db, row.department_id, student, new_date, already, added)

    apply_to_draft(row, change)
    return inverse


def revert_edit(session, message_id, staff):
    message = get_message(session.session_id, message_id)
    if message.response_type != "edit":
        raise 400
    if message.edit_status != "applied":
        raise 409                                # 이미 되돌렸거나 실패한 변경 (결정 11)

    apply_edit(session, message.inverse_change, staff)
    message.edit_status = "reverted"
```

- 검증 함수는 기존 것을 그대로 재사용한다 — 새 검증 로직을 만들지 않는다 (결정 6, 사실 G).
- 검증 대상 상태에 draft가 이미 포함돼 있다 (`_HOUR_LIMIT_CHECK_STATUSES = (draft, confirmed, manual)`, `routers/schedule.py:1525`).
- 다건 변경은 트랜잭션으로 all-or-nothing 처리한다. 부분 적용 상태를 남기지 않는다.

## 6. ⚠️ 알려진 위험

### 6.1 Gemini 쿼터 (v1에서 이어짐 — 의도적 트레이드오프)

**여러 턴 대화형(결정 1) + 쿼터 상한 없음(결정 2)의 조합은, 세션이 길어질수록 Gemini 무료 티어 일일 한도(20회)를 챗봇 하나가 전부 잠식시킬 수 있다.** 이 경우 같은 프로젝트 키를 공유하는 `review`, 대타 `ai-check` 기능까지 함께 막힌다.

이는 설계 과정에서 인지하고도 택한 선택이며, 버그가 아니다. 완화책: 세션/직원 단위 상한, 챗봇 전용 별도 키, 유료 티어 전환.

결정 13(LLM은 분류만)은 이 위험을 키우지 않는다 — 가중치 조정도 턴당 LLM 1회다.

### 6.2 재solve 지연 (v2 신규)

결정 14의 단일 워커 + 프로덕션 규모에서 solve가 30초 제한까지 갈 수 있다(사실 E). 대화 턴 안에서 동기로 기다리면 UX가 무너진다. 비동기 처리 또는 비교용 짧은 시간 제한이 필요하며, 구현 시 실측으로 판단한다.

### 6.3 `manual` 배치와의 상호작용 (v2 신규)

챗봇은 draft만 고치지만, 같은 학생에게 이미 `manual` 배치의 근무가 있으면 겹침 검증에서 걸린다(`_HOUR_LIMIT_CHECK_STATUSES`에 manual 포함). 이는 정상 동작이며, 실패 메시지에 "수동 등록된 근무와 겹칩니다"가 드러나도록 사유를 그대로 전달한다.

## 7. 스코프 밖 (이번 단계에서 하지 않음)

- 세션별/직원별 쿼터 상한 (섹션 6.1, 의도적 제외)
- 수동 수정분 pin 후 재solve — 고정이 늘수록 `INFEASIBLE` 위험이 커짐 (섹션 0.2). 이번 단계는 순서 강제 + 경고로 처리
- pairwise 비교로 선호 학습("A안 vs B안 중 뭐가 낫나요?") — solve 2회라 비용이 큼. 결정 13의 카테고리+방향 방식이 자리 잡은 뒤 검토
- 여러 변경을 한 번에 묶는 배치 편집 (결정 5는 단일 변경 유지)
- 되돌리기 스택의 다단계 undo/redo — 메시지 단위 1건 되돌리기만 제공
- `understaffing` 가중치 대화형 조정 (섹션 4.2에서 제외)
- 세션 목록 조회, 세션 삭제 등 부가 CRUD

## 8. 구현 착수 전 확인 필요

- **[선행 필수]** `solver.py`에 `random_seed`·`num_search_workers=1`을 넣고 동일 입력 2회가 동일 결과를 내는지 실측 확인 (결정 14, 섹션 4.3). **이 확인 전에는 가중치 대화 기능에 착수하지 않는다.**
- draft 배치의 근무 한 건을 이동·삭제하는 경로가 현재 없다 — 신설 필요 범위 확정 (사실 C)

- 프론트엔드에서 대화형 UI(메시지 리스트, 변경 카드 + 되돌리기 버튼, penalty before/after 표시)를 붙일 기존 컴포넌트 유무

## 9. eval 검증 계획

| 케이스 | 방식 | 목적 |
|---|---|---|
| 일반 질문 → `response_type: "answer"` | 실 Gemini 1회 | 답변 분류 정확도 |
| 변경 요청 → `response_type: "edit"` + 유효한 `applied_change` | 실 Gemini 1회 | 편집 분류와 스키마 적합성 |
| 가중치 불만 → `response_type: "tune"` + 올바른 카테고리·방향 | 실 Gemini 1회 | 결정 13 분류 정확도 (숫자를 지어내지 않는지 포함) |
| 편집 적용 → draft 배치만 변경, `manual`·`confirmed` 무변경 | mock | **사실 A·B 회귀 방지** — 학생 노출 경로를 건드리지 않음을 보장 |
| 편집 되돌리기 → `inverse_change` 적용 후 원상 복구, 재되돌리기 409 | mock | 결정 11 확인 |
| 검증 실패(겹침/주간 상한) → 변경 없음, `edit_status="failed"`, 사유 전달 | mock | 실패 처리와 무결성 확인 |

실 Gemini 호출은 3건으로 제한. 나머지 3건은 mock으로 쿼터 없이 검증한다.

네 번째 케이스는 v2에서 가장 중요한 회귀 테스트다 — 승인 게이트를 없앤 대가로, 쓰기 대상이 draft를 벗어나지 않는다는 것이 테스트로 고정돼야 한다.
