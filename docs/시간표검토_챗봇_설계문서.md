# 시간표 검토 챗봇 — 설계 문서

**작성일**: 2026-08-27
**관련 배경**: 되묻기(clarification) 기능, 대타 승인 AI 적합성 검사(`ai-check`) 기능의 연장선. 근무표 검토를 여러 턴 대화형 챗봇으로 확장하는 기능.
**전제**: 되묻기 인프라(`clarification_requests`, `clarification_answer`), `review` 기능, `POST /api/schedule/manual`(직원 수동 배정 API, #77에서 겹침·주간 상한 검증 완비)이 모두 구현·머지 완료된 상태.

---

## 0. 배경 및 목표

기존 `review`는 1회성 배치 호출로 findings/clarification_requests를 반환하는 stateless 구조다. 직원이 특정 배정에 대해 자유롭게 캐묻고("이건 왜 이래?", "이 학생 빼고 다시 봐줄 수 있어?"), 대화 중 나온 변경 아이디어를 그대로 승인해 반영할 수 있는 대화형 인터페이스가 필요하다는 문제의식에서 출발한다.

**핵심 원칙**: 챗봇은 텍스트로 답하고 변경은 "제안"할 뿐, 실제 반영은 기존 `manual` API를 통해서만 이뤄진다. "AI는 확정 권한이 없다"는 프로젝트 전체 원칙을 챗봇에서도 그대로 유지한다.

## 1. 결정 사항 요약

| # | 항목 | 결정 |
|---|---|---|
| 1 | 대화 범위 | 단일 배치 대화형 |

| 3 | 세션 저장 | 직원 × 세션 단위, DB 영속. 명시적 "새 대화 시작"으로만 리셋 |

| 5 | 제안 스키마 | 한 턴에 단일 변경만, `manual` API의 요청 body 형식을 그대로 재사용 |

| 9 | 세션 컨텍스트 | 세션 하나당 `batch_id` 하나에 고정 |
| 10 | 컨텍스트 관리 | Gemini 호출 시 최근 N턴만 포함 (오래된 건 잘라냄) |
| 11 | 제안 생명주기 | 1회성 — 승인 시도(성공/실패 불문) 후 같은 제안 재사용 불가, `pending`/`approved`/`failed` 상태 기록 |
| 12 | eval 검증 | 핵심 시나리오 4개 (섹션 9) |

## 2. 데이터 스키마

### `chat_session` (신설)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `session_id` | PK | |
| `batch_id` | FK → `schedule_batch` | 이 세션이 묶인 근무표 배치 (결정 9) |
| `staff_id` | FK → `staff` | 세션 시작 직원 (결정 3) |
| `created_at` | datetime | |
| `last_active_at` | datetime | 최근 메시지 시각, "새 대화 시작" 판단에 참고 가능 |

### `chat_message` (신설)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `message_id` | PK | |
| `session_id` | FK → `chat_session` | |
| `role` | str | `user` / `assistant` |
| `content` | text | 메시지 본문 (user 발화 또는 AI 텍스트 응답) |
| `response_type` | str, nullable | `assistant` 메시지에만: `answer` / `proposal` (결정 7) |
| `proposed_change` | jsonb, nullable | `response_type="proposal"`일 때만, `manual` API body 형식 (결정 5) |
| `proposal_status` | str, nullable | `pending` / `approved` / `failed` (결정 11). `proposal`이 아니면 NULL |
| `created_at` | datetime | |

**메모**: 신규 테이블이므로 되묻기/대타 기능 동일 판단 기준(SQLAlchemy `create_all()`로 자동 반영)이 적용될 것으로 예상되나, 구현 착수 전 재확인 필요(섹션 8).

## 3. API 스펙

### `POST /api/schedule/chat/sessions`
새 세션 생성. Body: `{ "batch_id": int }`. 응답: `{ "session_id": int, ... }`

### `GET /api/schedule/chat/sessions/{session_id}/messages`
대화 이력 전체 조회 (새로고침 후 복원용, 결정 3).

### `POST /api/schedule/chat/sessions/{session_id}/messages`
메시지 전송. Body: `{ "content": string }`. Gemini 호출 직전 — 최근 N턴(결정 10)을 컨텍스트로 포함해 프롬프트 조립.

응답 예시 (제안 케이스):
```json
{
  "message_id": 42,
  "role": "assistant",
  "content": "8/28 수요일 학생 배정을 13:00-18:00로 옮기는 건 어떨까요?",
  "response_type": "proposal",
  "proposed_change": {
    "schedule_id": 255,
    "student_id": "20211357",
    "start_time": "13:00:00",
    "end_time": "18:00:00"
  },
  "proposal_status": "pending"
}
```

### `POST /api/schedule/chat/sessions/{session_id}/proposals/{message_id}/approve`
제안 승인. `message_id`가 가리키는 `chat_message.proposed_change`를 그대로 `manual` API 로직에 전달.

- 성공: `proposal_status = "approved"`로 갱신, `manual` API의 성공 응답 그대로 반환
- 실패(겹침/상한 초과 등): `proposal_status = "failed"`로 갱신, `manual` API의 에러 메시지 그대로 반환. **재시도 불가** — 직원이 챗봇에 새 메시지로 다시 요청해야 함(결정 11)

## 4. 프롬프트 설계

**신규 파일**: `chat_system_prompt.md` (review, substitute_check와 별도 — 이 프로젝트의 기존 패턴대로 용도별 분리)

포함할 요소:
- 이 세션이 묶인 `batch_id`의 현재 근무표 상태, 부서 `custom_rules`를 컨텍스트로 주입
- 최근 N턴의 대화 이력
- **응답 스키마 강제**: `response_type`과, `proposal`인 경우 `proposed_change`가 정확히 `manual` API body 형식(schedule_id/student_id/start_time/end_time 등)을 따르도록 명시
- **원칙 문구**: "너는 변경을 제안할 뿐 실행하지 않는다. 실행 여부와 결과는 시스템이 별도로 처리한다."

## 5. 승인 처리 로직

```python
def approve_proposal(session_id, message_id, staff):
    message = get_message(session_id, message_id)
    if message.response_type != "proposal":
        raise 400  # 제안이 아닌 메시지 승인 시도
    if message.proposal_status != "pending":
        raise 409  # 이미 승인/실패 처리된 제안 (결정 11, 재사용 방지)

    try:
        result = manual_schedule_service.apply(message.proposed_change, staff)
        message.proposal_status = "approved"
        return result
    except ValidationError as e:
        message.proposal_status = "failed"
        raise  # manual API의 에러를 그대로 전달
```

`manual_schedule_service.apply()`는 기존 `POST /api/schedule/manual`의 처리 로직을 재사용 — 새 검증 로직을 만들지 않는다(결정 6).

## 6. ⚠️ 알려진 위험 — 의도적으로 감수한 트레이드오프

**여러 턴 대화형(결정 1) + 쿼터 상한 없음(결정 2)의 조합은, 세션이 길어질수록 Gemini 무료 티어 일일 한도(20회)를 챗봇 하나가 전부 잠식시킬 수 있다.** 이 경우 같은 프로젝트 키를 공유하는 `review`, 대타 `ai-check` 기능까지 함께 막힌다.

이는 설계 과정에서 인지하고도 택한 선택이며, 버그가 아니다. 다음 담당자가 실제 운영 중 이 문제를 겪는다면 고려할 수 있는 완화책:
- 세션/직원 단위별 상한 도입 (예: 세션 하나당 N턴)
- 챗봇 전용 별도 Gemini 키/프로젝트 분리
- 유료 티어 전환

## 7. 스코프 밖 (이번 단계에서 하지 않음)

- 세션별/직원별 쿼터 상한 (섹션 6 참고, 의도적 제외)
- 제안 사전 검증(결정 6) — 승인 전 "통과 여부 미리보기" 기능은 다음 단계 과제
- 여러 변경을 한 번에 묶는 배치 제안 (결정 5에서 단일 변경으로 한정)
- 멀티턴 컨텍스트 유지 중 Gemini 검증 (eval에서 mock으로만 확인, 섹션 9)
- 세션 목록 조회, 세션 삭제 등 부가 CRUD — 필요성이 확인되면 추후 추가

## 8. 구현 착수 전 확인 필요 (코드 조사 우선)

- `chat_session`/`chat_message`가 신규 테이블인지 재확인 (되묻기/대타 기능과 동일 판단 기준 적용 여부)
- `manual` API의 실제 처리 로직이 승인 로직에서 함수 단위로 재사용 가능한 형태로 분리돼 있는지 (라우터 안에 인라인으로 있다면 리팩터링 필요 여부 판단)
- `review.py`/`substitute_check.py`의 Gemini 호출 헬퍼(`_get_gemini_client()` 등) 재사용 가능 범위 재확인 (대타 기능 조사 때처럼 일부만 재사용 가능할 수 있음)
- 프론트엔드에서 대화형 UI(메시지 리스트, 제안 카드 + 승인 버튼)를 붙일 기존 컴포넌트 유무

## 9. eval 검증 계획

| 케이스 | 방식 | 목적 |
|---|---|---|
| 일반 질문 → `response_type: "answer"` | 실 Gemini 1회 | 답변 분류 정확도 확인 |
| 변경 요청 → `response_type: "proposal"` + 유효한 `proposed_change` | 실 Gemini 1회 | 제안 생성과 스키마 적합성 확인 |
| 제안 승인 → `manual` API 정상 반영 | mock (LLM 호출 없음) | 승인 파이프라인 정확도 확인 |
| 제안 승인 → `manual` 검증 실패(겹침 등) → 에러 그대로 전달, `proposal_status="failed"`, 재시도 불가 확인 | mock (LLM 호출 없음) | 실패 처리와 1회성 원칙(결정 11) 확인 |

실 Gemini 호출은 2건으로 최소화. 나머지 2건은 mock으로 쿼터 없이 검증 가능.
