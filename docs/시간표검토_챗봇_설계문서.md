# 시간표 검토 챗봇 — 설계 문서

**작성일**: 2026-08-27
**개정일**: 2026-08-28 (v2 — 에이전트 전환·가중치 튜닝, 섹션 0.1 / v3 — 툴 호출 구조 전환, 섹션 0.3)
**관련 배경**: 되묻기(clarification) 기능, 대타 승인 AI 적합성 검사(`ai-check`) 기능의 연장선. 근무표 검토를 여러 턴 대화형 챗봇으로 확장하는 기능.
**전제**: 되묻기 인프라(`clarification_requests`, `clarification_answer`), `review` 기능, `POST /api/schedule/manual`(직원 수동 배정 API, #77에서 겹침·주간 상한 검증 완비)이 모두 구현·머지 완료된 상태.

---

## 0. 배경 및 목표

기존 `review`는 1회성 배치 호출로 findings/clarification_requests를 반환하는 stateless 구조다. 직원이 특정 배정에 대해 자유롭게 캐묻고("이건 왜 이래?", "이 학생 빼고 다시 봐줄 수 있어?"), 대화 중 나온 변경 아이디어를 그대로 반영할 수 있는 대화형 인터페이스가 필요하다는 문제의식에서 출발한다.

**핵심 원칙**: 챗봇은 **draft(제안) 근무표만** 고친다. 확정(`confirm`)은 사람만 한다. "AI는 확정 권한이 없다"는 프로젝트 전체 원칙은 유지하되, 그 게이트를 턴마다가 아니라 확정 시점 한 곳에 둔다.

## 0.1 v2 개정 배경

v1은 AI가 변경을 "제안"만 하고 직원이 턴마다 승인 버튼을 눌러야 반영되는 구조였다. 두 가지 피드백에서 개정이 출발한다.

1. **가중치를 대화로 찾자.** 현재 soft constraint 가중치는 임의로 정한 값이고 실제 사용자의 체감과 다를 수 있다. 대화하면서 적절한 가중치를 좁혀 나가는 방식이 낫다.
2. **제안만 하는 건 번거롭다.** draft 시간표를 바꾸는 것이니 AI가 직접 반영하고, 결정(확정)만 사람이 하면 된다.

### 개정 착수 전 코드 조사 결과 (v1 섹션 8의 선행 조사)

조사 결과 v1 설계의 **핵심 전제 두 개가 실제 코드와 어긋난다**는 것이 확인됐다.

## 0.2 두 기능의 관계 — 순서를 강제한다

가중치 조정(전역 재배치)과 개별 편집(국소 수정)은 **서로 충돌한다.** 챗봇으로 손수 고쳐 놓은 배정이 있는 상태에서 가중치를 바꿔 재solve하면 그 수정이 전부 사라진다. 사용자는 같은 대화창 안에서 이 둘을 구분하지 못한다.

이번 단계에서는 **순서 강제**로 해결한다.

```text
① 가중치 대화 (전역 튜닝, 재solve)  →  ② 개별 편집 (국소 수정)  →  ③ 확정
```

- ② 이후 ①로 되돌아가는 요청이 오면 "수동 수정 N건이 사라집니다"를 경고하고 사용자 확인을 받는다.
- 수동 수정분을 hard constraint로 고정(pin)한 채 재solve하는 방식은 고정이 늘수록 `INFEASIBLE` 위험이 커지므로 이번 단계 스코프 밖으로 둔다(섹션 7).

## 0.3 v3 개정 배경 — 분류기에서 툴 호출로

v2까지의 설계는 **에이전트가 아니라 분류기**였다. LLM을 턴당 1회 호출해 `answer`/`edit`/`tune` 중 하나로 분류한 JSON을 받고, 파이썬이 그 값으로 분기하는 구조다. 기존 `review`·`substitute_check`가 쓰는 구조화 출력(`response_mime_type="application/json"` + `response_schema`) 패턴을 그대로 이은 것으로, 백엔드 어디에도 함수 호출(`tools=`)을 쓰는 코드는 없다.

**Gemini 유료 티어로 전환**하면서 전제가 바뀌었다. v2에서 툴 루프를 포기한 유일한 이유가 무료 티어 일일 20회 한도였고, 그 제약이 사라졌다.

### 병목은 사라진 게 아니라 옮겨갔다

LLM 호출은 이제 턴당 여러 번 해도 되지만, **재solve는 여전히 30초**다(사실 E, `LOG.md` 실측). v3 설계의 비용 기준은 "LLM을 몇 번 부르는가"가 아니라 **"solve를 몇 번 돌리는가"**다.

### 왜 soft constraint 자체를 툴로 만들지 않았는가

"각 soft constraint를 지키게 하는 툴"(`enforce_meal_break()` 등)을 두는 안을 검토했으나 채택하지 않았다.

- **soft constraint는 개별로 지킬 수 있는 대상이 아니다.** CP-SAT은 11개 페널티의 가중합을 한꺼번에 최소화한다. 하나만 따로 0으로 만드는 것은 다른 페널티를 얼마나 희생하느냐의 문제지 켜고 끄는 스위치가 아니다. "이 제약을 지켜라"는 결국 "가중치를 올리고 전체를 다시 풀어라"가 되어 `adjust_weight`와 같아진다.
- **툴 하나가 시간표 전체를 흔든다.** 툴 호출의 장점은 국소성인데 제약 툴은 전역 재배치를 유발한다. 연쇄 호출 3회면 solve가 3번 돌고 앞의 두 결과는 버려진다.
- **툴 정의만 11배로 늘고 표현력은 같다.** `adjust_weight(category, direction)` 하나가 모델에게도 더 명확하다.

대신 이 아이디어를 **읽기 툴로 뒤집어** 채택했다. `explain_penalty(category)`는 그 제약이 지금 어디서 누구에게 몇 점 발생 중인지 실제 위반 이벤트로 반환한다. `PenaltyEvent`(`name`/`cost`/`amount`/`student_id`/`day`/`minute`, docstring에 "설명 기능용"으로 명시)가 이미 있어 새로 만들 게 없고, solve를 돌리지 않으므로 싸고 빠르다.

### 툴 3층 구조

| 층 | 툴 | 비용 | 턴당 상한 |
|---|---|---|---|
| 읽기 | `find_schedules`, `explain_penalty(category)`, `get_student_availability`, `get_period_calendar`, `verify_schedule` | 쌈 | 스텝 예산 K 안에서 자유 |
| 쓰기 · 국소 | `move_schedule`, `remove_schedule`, `add_schedule` | 쌈 | 스텝 예산 K 안에서 자유 |
| 쓰기 · 전역 | `adjust_weight(category, direction)` + 재solve | **30초** | **1회** |

**전역 툴 턴당 1회 상한**이 핵심 안전장치다. 이것이 없으면 한 턴에 solve가 여러 번 돌고 중간 결과가 전부 버려진다. 가중치를 더 만지고 싶으면 다음 턴에 하면 되고, 그 사이 사람이 결과를 본다.

### 읽기 툴이 해결하는 문제 — `schedule_id` 환각

v2 설계는 draft 근무표 상태를 프롬프트에 통째로 주입하고 LLM이 거기서 `schedule_id`를 뽑게 했다. 최근 N턴만 컨텍스트에 넣으므로(결정 10) 배정이 잘려 나가면 **존재하지 않는 `schedule_id`를 지어낼 수 있고**, 그러면 검증 단계에서 튕기며 턴이 끝난다.

`find_schedules` 읽기 툴이 있으면 조회한 뒤 그 결과로 편집한다. 툴 호출 구조가 이 문제를 구조적으로 없앤다.

### v2에서 유지되는 것

쓰기 경계(draft만 수정)와 되돌리기(역연산 기록)는 **툴 구현 안에 그대로 남는다** — v2의 `inverse_change`가 v3에서는 각 쓰기 툴 호출의 `inverse` 항목이 된다. 섹션 0.1의 사실 A~G, 섹션 0.2의 순서 강제, 섹션 4.4의 결정적 재solve도 모두 유효하다. v3에서 바뀌는 것은 디스패치 방식(§4)과 메시지 스키마(§2)이며, 턴당 단일 변경이 아니라 변경 목록이 되면서 되돌리기가 "이 턴의 변경 N건 일괄 되돌리기"가 된다.

| `role` | str | `user` / `assistant` |
| `content` | text | 메시지 본문 |
| `tool_calls` | jsonb, nullable | `assistant` 메시지에만: 이 턴에 실행된 툴 호출 목록. 각 항목은 `{tool, args, result, inverses}` (결정 7·11). `inverses`는 그 호출이 적용한 순서대로의 역연산 배열 — #222 이전에 저장된 이력은 단수 `inverse`이며 되돌리기가 두 형태를 모두 읽는다 |
| `turn_status` | str, nullable | `applied` / `reverted` / `partial_failed` / `budget_exceeded` (결정 11·17) |
| `created_at` | datetime | |

**`tool_calls[].inverse`가 되돌리기의 근거다.** 승인 게이트를 없애는 대신, 쓰기 툴은 실행 시 반드시 역연산을 함께 기록한다. 읽기 툴은 `inverse`가 없다(되돌릴 것이 없으므로).

턴 되돌리기는 이 목록의 쓰기 항목을 **역순으로** 취소한다. 예를 들어 한 턴에서 `move` → `remove`가 실행됐다면 `remove` 복원 → `move` 복원 순으로 되돌린다.

`penalty_diff`처럼 `adjust_weight` 호출에만 딸리는 값은 해당 항목의 `result` 안에 담는다 — 메시지에 별도 컬럼을 두지 않는다.

**메모**: 신규 테이블이므로 되묻기/대타 기능과 동일 기준(SQLAlchemy `create_all()` + `schema_patches.py`)이 적용될 것으로 예상되나, 구현 착수 전 재확인 필요(섹션 8).

## 3. API 스펙

### `POST /api/schedule/chat/sessions`
새 세션 생성. Body: `{ "department_id": int, "period_start": date, "period_end": date }`. 해당 기간의 draft 배치를 찾아 `batch_id`에 캐시한다. draft가 없으면 400.

### `GET /api/schedule/chat/sessions/{session_id}/messages`
대화 이력 전체 조회 (새로고침 후 복원용, 결정 3).

### `POST /api/schedule/chat/sessions/{session_id}/messages`
메시지 전송. Body: `{ "content": string }`. 최근 N턴(결정 10)을 컨텍스트로 포함해 Gemini 호출 → 분류 결과에 따라 분기한다.

응답 예시 — 읽기 툴로 대상을 확인한 뒤 편집한 턴. 변경은 이미 적용된 상태로 반환된다.

```json
{
  "message_id": 42,
  "role": "assistant",
  "content": "20211357 학생의 8/28 수요일 근무를 13:00-18:00로 옮겼습니다. 되돌리려면 알려주세요.",
  "tool_calls": [
    {
      "tool": "find_schedules",
      "args": { "student_id": "20211357", "work_date": "2026-08-28" },
      "result": [{ "schedule_id": 255, "start_time": "09:00:00", "end_time": "14:00:00" }]
    },
    {
      "tool": "move_schedule",
      "args": { "schedule_id": 255, "start_time": "13:00:00", "end_time": "18:00:00" },
      "result": { "ok": true },
      "inverse": { "tool": "move_schedule", "args": { "schedule_id": 255, "start_time": "09:00:00", "end_time": "14:00:00" } }
    }
  ],
  "turn_status": "applied"
}
```

`find_schedules`가 먼저 불린 것이 v3의 요점이다 — `schedule_id`를 프롬프트 컨텍스트에서 추측하지 않고 조회해서 쓴다(섹션 0.3).

가중치 조정 턴의 `adjust_weight` 항목 예시:

```json
{
  "tool": "adjust_weight",
  "args": { "category": "meal_missed", "direction": "up" },
  "result": {
    "scale": { "before": 1.0, "after": 1.5 },
    "penalty_diff": {
      "before": { "meal_missed": 60, "preferred_slot_miss": 12 },
      "after":  { "meal_missed": 20, "preferred_slot_miss": 21 }
    },
    "solver": { "status": "FEASIBLE", "solve_time_seconds": 30.0 }
  },
  "inverse": { "tool": "adjust_weight", "args": { "category": "meal_missed", "direction": "down" } }
}
```

쓰기 툴이 검증(겹침·주간 상한)에 걸리면 그 툴만 실패로 기록되고 실패 사유가 모델에게 반환된다. 모델은 남은 스텝 예산 안에서 다른 방법을 시도하거나 사용자에게 사유를 설명할 수 있다. 턴이 끝났을 때 실패한 쓰기가 하나라도 있으면 `turn_status: "partial_failed"`로 남긴다.

### `POST /api/schedule/chat/sessions/{session_id}/messages/{message_id}/revert`
그 턴의 쓰기 툴 호출을 **역순으로** 일괄 취소하고 `turn_status = "reverted"`로 갱신한다 (결정 11).

- 이미 `reverted`인 턴: 409
- 되돌린 턴은 재적용 불가 — 사용자가 새 메시지로 다시 요청해야 한다
- 되돌리기 도중 일부가 실패하면(그 사이 다른 편집이 끼어든 경우) 전체를 롤백하고 409로 알린다 — 부분 복구 상태를 남기지 않는다

### `POST /api/schedule/chat/sessions/{session_id}/weights/persist`
세션의 `session_weight_scales`를 부서 기본값(`department_policy.soft_weight_scales`)으로 저장한다 (결정 15). 기존 PATCH 경로(`routers/schedule.py:1093-1099`)를 재사용한다.

## 4. 툴·프롬프트 설계

**신규 파일**: `chat_system_prompt.md` (review, substitute_check와 별도 — 기존 패턴대로 용도별 분리)

기존 두 기능은 구조화 출력(`response_mime_type` + `response_schema`)을 쓰지만, 챗봇은 `google-genai`의 함수 호출(`tools=`)을 쓴다. 백엔드에서 함수 호출을 쓰는 첫 사례이므로 클라이언트 헬퍼 재사용 범위를 착수 전에 확인한다(섹션 8).

### 4.1 시스템 프롬프트

포함할 요소:
- 이 세션이 다루는 기간·부서, 부서 `custom_rules`, 현재 `penalty_breakdown` **총계**
- 최근 N턴의 대화 이력
- **원칙 문구**: "너는 제안(draft) 근무표만 고칠 수 있다. 확정은 사람만 한다. 네가 고친 내용은 되돌릴 수 있다."
- **조회 우선 지시**: "근무를 고치기 전에 반드시 `find_schedules`로 대상을 확인하라. `schedule_id`를 추측하지 마라."
- **스텝 예산 고지**: 턴당 툴 호출 K회 상한과, 초과 시 요청을 나눠 달라고 답해야 한다는 지시

draft 근무표 **전체를 프롬프트에 주입하지 않는다.** 총계만 넣고 세부는 읽기 툴로 조회하게 한다 — 이것이 컨텍스트 절단으로 인한 `schedule_id` 환각을 없애는 방식이다(섹션 0.3).

### 4.2 툴 정의

**읽기 툴** — solve를 돌리지 않는다. 스텝 예산 안에서 자유롭게 호출 가능.

| 툴 | 인자 | 반환 |
|---|---|---|
| `find_schedules` | `student_name?`, `student_id?`, `weekday?`, `work_date?`, `date_from?`, `date_to?` | 조건에 맞는 draft 근무 목록 — `schedule_id`·이름·날짜·요일(`day`)·시각. 정의되지 않은 인자는 무시하지 않고 오류로 돌려준다 (#213) |
| `explain_penalty` | `category` | 그 카테고리에서 실제 발생한 위반 이벤트 — 학생·날짜·시각·비용 (`PenaltyEvent` 기반) |
| `get_student_availability` | `student_id` | 그 학생의 요일 반복 가능 시간·수업 시간 + 기간 안의 날짜별 예외(`AvailabilityException`) |
| `get_period_calendar` | `date_from?`, `date_to?` | 기간의 날짜별 학사 일정 — 공휴일·교내 휴강일·폐관일·시험 기간·학기/방학과 그날의 부서 개관 시간. 주차별 요약(`weeks`)과 날짜별 목록(`days`) |
| `verify_schedule` | 없음 | 현재 draft의 hard constraint 위반 목록 — `ok`, `critical_count`, `warning_count`, `violations`(규칙·심각도·학생·시각·메시지), `omitted` |

`explain_penalty`가 결정 18의 산물이다. "각 soft constraint를 지키게 하는 툴"을 두는 대신, 그 제약이 **지금 어디서 위반되고 있는지 근거를 조회**하는 읽기 툴로 뒤집었다(섹션 0.3).

**쓰기 툴 · 국소** — draft 배치만 건드린다. 검증은 기존 함수 재사용(결정 6).

| 툴 | 인자 | 역연산 |
|---|---|---|
| `move_schedule` | `schedule_ids`, `work_date?`(1건일 때만), `start_time`, `end_time` | 각 건을 이전 날짜·시각으로 되돌리는 `move_schedule` 목록 |
| `remove_schedule` | `schedule_ids` | 삭제된 근무들을 복원하는 `add_schedule` 목록 |
| `add_schedule` | `student_id`, `work_dates`, `start_time`, `end_time` | 추가된 근무들을 지우는 `remove_schedule` 목록 |

**개정 (#222)** — 원설계의 쓰기 툴은 인자가 단수(`schedule_id`)라 한 호출이 한 건만
고쳤다. 그러면 "다 빼줘"류 요청의 한 턴 상한이 `find_schedules` 1회 + 쓰기 4회가 되어,
대상이 5건 이상이면 예산이 소진되며 **앞 4건만 지워진 채** `budget_exceeded`로 끝났다.
그래서 인자를 배열로 바꾸고, 호출 하나를 원자 단위로 만들었다 — 한 건이라도 실패하면
SAVEPOINT를 되감아 그 호출은 아무것도 적용하지 않는다. 부분 적용 상태를 만들지 않는
것이 목적이므로, 역연산도 "전부 기록되거나 하나도 기록되지 않는다"
(`tool_calls[].inverses`, 적용 순서대로). 한 호출당 상한은 `CHAT_MAX_EDIT_ITEMS`(기본 20).

**쓰기 툴 · 전역** — 재solve를 유발한다. **턴당 1회**(결정 16).

| 툴 | 인자 | 역연산 |
|---|---|---|
| `adjust_weight` | `category` (enum, `understaffing` 제외), `direction` (`up`/`down`) | 반대 방향 `adjust_weight` |

### 4.3 가중치 조정 — 툴 시그니처가 숫자를 막는다 (결정 13)

"`meal_missed`를 20에서 30으로" 같은 숫자를 LLM이 직접 고르게 하면 근거 없이 요동친다. v2는 이를 파이프라인 규칙으로 막았지만, v3에서는 **툴 시그니처 자체로 강제**한다 — `direction`이 `up`/`down` enum이라 모델이 배율을 표현할 방법이 없다.

```text
사용자 자연어 불만
  → 모델이 adjust_weight(category, direction) 호출
  → 시스템이 고정 스텝으로 배율 적용 (up = ×1.5, down = ×0.67)
  → 결정적 재solve (결정 14)
  → penalty_breakdown before/after를 툴 결과로 모델에게 반환
  → 모델이 트레이드오프를 사용자 말로 설명
```

`understaffing`(1000)은 hard에 준하는 값이므로 **enum에서 제외**한다. 조정 대상 10개는 `config/departments/library_info_service.json`의 `soft_weights` 중 나머지다: `preferred_slot_miss`(3), `block_start`(4), `non_campus_day`(5), `fair_hours_shortfall`(6), `morning_days_excess`(10), `consecutive_morning_excess`(10), `avoid_range_slot`(12), `morning_after_close`(15), `meal_missed`(20), `exam_proximity`(25).

### 4.4 결정적 재solve (결정 14)

사실 E에 따라, 가중치를 바꾸지 않아도 재생성만으로 시간표가 달라진다. 비교가 성립하려면 재solve를 결정적으로 만들어야 한다.

- `solver.parameters.random_seed` 고정
- `solver.parameters.num_search_workers = 1`
- 동일 `time_limit_seconds` 사용

**선행 작업**: 이 파라미터 설정은 `scheduler/engine/solver.py`에 현재 없다(사실 E). 챗봇 구현 착수 전에 먼저 넣고, 동일 입력 2회 실행이 동일 결과를 내는지 실측으로 확인해야 한다. 이 확인 없이 가중치 대화 기능을 만들면 노이즈에 반응하는 챗봇이 된다.

**부작용**: 단일 워커는 느리다. 프로덕션 규모에서 이미 30초 제한에 걸려 `FEASIBLE`로 끝나므로(사실 E), 대화 턴 안에서 동기로 돌리기에는 길다. 비동기 처리 또는 비교용 짧은 `time_limit` 사용을 함께 검토한다.

## 5. 툴 루프·되돌리기 처리 로직

### 5.1 턴 실행

```python
def run_turn(session, user_text, staff):
    calls, global_used = [], False

    for _ in range(STEP_BUDGET):                 # 결정 17 — 기본 5
        resp = gemini.generate(prompt(session, user_text, calls), tools=TOOLS)
        if not resp.tool_call:
            return finish(session, resp.text, calls)

        name, args = resp.tool_call

        if name in GLOBAL_TOOLS:                 # 결정 16 — 재solve 유발
            if global_used:
                calls.append(refused(name, "전역 툴은 턴당 1회만 호출할 수 있습니다"))
                continue
            global_used = True

        calls.append(execute(session, name, args, staff))   # 실패해도 사유를 담아 모델에 반환

    return finish(session, budget_exceeded_message(), calls, status="budget_exceeded")
```

- 툴 실패는 예외로 turn을 끝내지 않는다. 사유를 결과로 모델에게 돌려주어 남은 예산 안에서 다른 방법을 시도하게 한다.
- 쓰기 툴은 실행 시 역연산을 함께 기록한다 (`calls[i].inverse`).
- 쓰기 툴은 draft 배치만 건드린다 — `manual`·`confirmed`는 대상이 아니다 (사실 A·B).
- 검증 함수는 기존 것을 그대로 재사용한다 (결정 6, 사실 G). 검증 대상 상태에 draft가 이미 포함돼 있다 (`_HOUR_LIMIT_CHECK_STATUSES = (draft, confirmed, manual)`, `routers/schedule.py:1525`).

### 5.2 턴 되돌리기

```python
def revert_turn(session, message_id, staff):
    message = get_message(session.session_id, message_id)
    if message.turn_status == "reverted":
        raise 409                                # 이미 되돌린 턴 (결정 11)

    writes = [c for c in message.tool_calls if c.get("inverse")]
    with transaction():                          # 부분 복구 상태를 남기지 않는다
        for call in reversed(writes):            # 역순 취소
            execute(session, call["inverse"]["tool"], call["inverse"]["args"], staff)
    message.turn_status = "reverted"
```

- 되돌리기 도중 하나라도 실패하면(그 사이 다른 편집이 끼어든 경우) 전체를 롤백하고 409로 알린다.
- `adjust_weight`의 역연산은 반대 방향 호출이며 **재solve를 한 번 더 유발한다** — 되돌리기도 30초가 걸릴 수 있다.

## 6. ⚠️ 알려진 위험

### 6.1 비용 — 병목이 LLM에서 solver로 옮겨갔다 (v3 개정)

v1·v2의 위험은 Gemini 무료 티어 일일 20회 한도였다. **유료 티어 전환으로 이 제약은 해소됐다.** 툴 루프가 턴당 LLM을 여러 번 부르는 것은 이제 문제가 아니다.

대신 실제 비용 기준이 바뀌었다. **비싼 것은 재solve(30초)이지 LLM 호출이 아니다.** 그래서 통제 수단도 바뀐다.

- **전역 툴 턴당 1회**(결정 16) — 한 턴에 solve가 여러 번 돌고 중간 결과가 버려지는 것을 막는다
- **스텝 예산 K**(결정 17) — 모델이 툴 루프에서 무한히 도는 것을 막는다. 읽기 툴은 싸므로 K는 넉넉히 잡아도 되지만, 상한 자체는 있어야 한다

남은 위험은 **예산 소진 자체**다. 유료 티어라도 무제한은 아니므로, 운영 중 사용량을 관찰해 세션/직원 단위 상한이 필요한지 판단한다. 이번 단계에서는 상한을 두지 않는다(섹션 7).

### 6.2 재solve 지연 (v2 신규, v3에서 더 중요해짐)

결정 14의 단일 워커 + 프로덕션 규모에서 solve가 30초 제한까지 갈 수 있다(사실 E). 대화 턴 안에서 동기로 기다리면 UX가 무너진다.

v3에서 이 위험이 커졌다. 툴 루프 안에서 `adjust_weight`가 불리면 **모델이 응답을 마치기 전에** 30초가 소모되고, 되돌리기도 재solve를 한 번 더 유발한다(섹션 5.2). 비동기 처리 또는 비교용 짧은 시간 제한이 필요하며, 구현 시 실측으로 판단한다.

### 6.3 `manual` 배치와의 상호작용 (v2 신규)

챗봇은 draft만 고치지만, 같은 학생에게 이미 `manual` 배치의 근무가 있으면 겹침 검증에서 걸린다(`_HOUR_LIMIT_CHECK_STATUSES`에 manual 포함). 이는 정상 동작이며, 실패 메시지에 "수동 등록된 근무와 겹칩니다"가 드러나도록 사유를 그대로 전달한다.

### 6.4 툴 루프 폭주 (v3 신규)

모델이 같은 툴을 반복 호출하거나 편집을 넣었다 뺐다 하며 예산을 소진할 수 있다. 스텝 예산(결정 17)이 상한을 보장하지만, 예산을 다 쓰고 아무것도 못 한 턴에서도 **이미 적용된 쓰기는 남는다.** 이 경우 `turn_status: "budget_exceeded"`로 기록하고, 사용자가 그 턴을 통째로 되돌릴 수 있게 한다.

## 7. 스코프 밖 (이번 단계에서 하지 않음)

- 세션별/직원별 예산 상한 (섹션 6.1 — 운영 중 사용량을 보고 판단)
- 수동 수정분 pin 후 재solve — 고정이 늘수록 `INFEASIBLE` 위험이 커짐 (섹션 0.2). 이번 단계는 순서 강제 + 경고로 처리
- pairwise 비교로 선호 학습("A안 vs B안 중 뭐가 낫나요?") — solve 2회라 비용이 큼. 결정 13의 방향 조정 방식이 자리 잡은 뒤 검토
- soft constraint별 강제 툴 (결정 18 — `explain_penalty` 읽기 툴로 대체)
- 전역 툴 턴당 2회 이상 (결정 16 — solve 시간이 감당되는지 확인된 뒤 완화 검토)
- 되돌리기 스택의 다단계 undo/redo — 턴 단위 1건 되돌리기만 제공
- `understaffing` 가중치 조정 (섹션 4.3에서 enum 제외)
- 세션 목록 조회, 세션 삭제 등 부가 CRUD

## 8. 구현 착수 전 확인 필요

- **[선행 필수]** `solver.py`에 `random_seed`·`num_search_workers=1`을 넣고 동일 입력 2회가 동일 결과를 내는지 실측 확인 (결정 14, 섹션 4.4). **이 확인 전에는 가중치 조정 툴에 착수하지 않는다.**
- draft 배치의 근무 한 건을 이동·삭제하는 경로가 현재 없다 — 쓰기 툴이 호출할 서비스 계층 범위 확정 (사실 C)
- **함수 호출(`tools=`)은 이 백엔드에서 첫 사례다.** 기존 두 기능은 구조화 출력만 쓴다(`review.py:407`, `substitute_check.py:326`). `google-genai` 함수 호출 사용법과, `_get_gemini_client()` 등 기존 헬퍼·재시도 로직의 재사용 가능 범위를 확인한다
- 툴 호출 실패·거부를 모델에 되돌려주는 형식(오류 메시지를 툴 result로 반환)이 현재 SDK 버전에서 어떻게 표현되는지 확인
- `chat_session`/`chat_message` 신규 테이블 반영 방식 재확인 (`create_all()` + `schema_patches.py`)
- 스텝 예산 K 초기값(5)이 실제 요청에 충분한지 — 읽기 1~2회 + 쓰기 1~3회를 상정했으나 실측으로 조정
- 프론트엔드에서 대화형 UI(메시지 리스트, 툴 호출 내역 + 턴 되돌리기 버튼, penalty before/after 표시)를 붙일 기존 컴포넌트 유무

## 9. eval 검증 계획

| 케이스 | 방식 | 목적 |
|---|---|---|
| 일반 질문 → 툴 호출 없이 답변 | 실 Gemini | 불필요한 툴 호출을 하지 않는지 |
| 변경 요청 → `find_schedules` **먼저** 호출한 뒤 `move_schedule` | 실 Gemini | **결정 0.3 핵심** — `schedule_id`를 추측하지 않고 조회하는지 |
| "왜 이래?" 질문 → `explain_penalty` 호출 후 근거 있는 답변 | 실 Gemini | 결정 18 — 읽기 툴이 실제로 쓰이는지 |
| 가중치 불만 → `adjust_weight(category, direction)` 호출 | 실 Gemini | 결정 13 — 올바른 카테고리·방향을 고르는지 |
| 다단계 요청 → 쓰기 툴 여러 번 호출로 완결 | 실 Gemini | 결정 5 — v2가 못 하던 것이 되는지 |
| 쓰기 툴 실행 → draft 배치만 변경, `manual`·`confirmed` 무변경 | mock | **사실 A·B 회귀 방지** — 학생 노출 경로를 건드리지 않음을 보장 |
| 턴 되돌리기 → 쓰기 역순 취소로 원상 복구, 재되돌리기 409 | mock | 결정 11 확인 |
| 전역 툴 2회 호출 시도 → 두 번째 거부, solve 1회만 실행 | mock | **결정 16 확인** — 한 턴에 solve가 여러 번 돌지 않음 |
| 스텝 예산 초과 → 루프 종료, `turn_status="budget_exceeded"`, 적용분은 되돌리기 가능 | mock | 결정 17·섹션 6.4 확인 |
| 검증 실패(겹침/주간 상한) → 그 툴만 실패, 사유가 모델에 반환됨 | mock | 실패 처리와 루프 지속 확인 |

유료 티어 전환으로 실 Gemini 호출 건수 제한은 완화됐다. 다만 mock으로 충분한 케이스는 계속 mock으로 둔다 — 빠르고 결정적이기 때문이지 쿼터 때문이 아니다.

**가장 중요한 두 케이스**:
- `manual`·`confirmed` 무변경 — 승인 게이트를 없앤 대가로, 쓰기 대상이 draft를 벗어나지 않는다는 것이 테스트로 고정돼야 한다 (v2에서 이어짐)
- 전역 툴 1회 제한 — 이것이 풀리면 한 턴에 30초 × N이 되어 UX가 무너진다 (v3 신규)
